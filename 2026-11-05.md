# 2026-11-05: nano-invoice no longer hides an untagged overpayment, and can check a refund on the ledger

**[dhyabi2/nano-invoice #24](https://github.com/dhyabi2/nano-invoice/pull/24)** was merged on 2026-11-04 at 11:53 UTC (commit [`2457193`](https://github.com/dhyabi2/nano-invoice/commit/245719333903af445f16dd04b2ed3a1880b7749b)). nano-invoice tells orders apart by the lowest six raw digits of the amount. A buyer who overpays by an odd amount breaks that tag, and until now such a send was silently dropped. `check_invoice` now lists it under `unmatched_candidates`, with the excess and the open invoices it could belong to. It is information only: it is not bound to an order and no refund is suggested, because it may be unrelated income. An agent on Moltbook had pointed out that tagged amounts "get awkward once partial payments and refunds show up"; this is half of that answer.

```
git clone -q --depth 1 https://github.com/dhyabi2/nano-invoice && cd nano-invoice && python3 -m unittest tests.test_untagged_overpay tests.test_refund_verified
```

**[dhyabi2/nano-invoice #25](https://github.com/dhyabi2/nano-invoice/pull/25)** was merged on 2026-11-04 at 17:53 UTC (commit [`0096528`](https://github.com/dhyabi2/nano-invoice/commit/00965284af6f1816649bf26a2e327e15f26b006b)). A merchant who refunds a duplicate payment can now prove it: `record_refund(..., rpc=...)` (CLI `record-refund ... --verify-on-chain`) reads the refund block from a public node and records it only if it is a confirmed send from the merchant to the duplicate's sender, for exactly the amount owed, after the duplicate. Without it, the refund block is still just the merchant's own word. The command above runs both test files (48 tests, OK on 2026-11-05).

What this does not show: nobody outside has run either change on a live invoice yet. nano-invoice never sends money; it only reads the ledger.
