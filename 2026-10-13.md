# 2026-10-13: three Nano payment tools no longer lose a payment, a vote, or settle one payment twice

Window: 2026-10-12 05:20 UTC to 2026-10-13 05:20 UTC. Each item below is a merged pull request on a public
repository that agents install to take or verify Nano (XNO) payments.

**A facilitator could settle one Nano payment several times.** In `nano-mcp`, the single-use claim key was built from
the block hash exactly as the caller spelled it, and a trailing newline passed the proof check, so the same confirmed
payment could be claimed again for the same request in another spelling. The proof must now be exactly 64 hex
characters and the claim key is the upper-cased hash, so every spelling of one payment maps to one claim. A malformed
proof is refused as invalid instead of raising an exception. Custom claim stores need an upper-case key as an upgrade
step; the built-in store migrates itself. https://github.com/dhyabi2/nano-mcp/pull/29

**A small send could close an invoice before the buyer paid it.** In `nano-invoice`, dust that carried an invoice's
public tag could close the invoice as underpaid, which then turned the buyer's exact payment into a duplicate. A send
below the invoice amount is now recorded as short and bound to nothing while the invoice is open. An overpayment
still settles at once. At expiry the earliest short send closes the invoice as underpaid and the others are refunded
as duplicates. https://github.com/dhyabi2/nano-invoice/pull/17

**Every payment silently changed the paying account's representative.** In `nano-mcp-public`, the wallet never asked
the node for the account's representative, so each send and receive signed a fallback one and moved the account's
voting weight without a warning. Amounts and destinations were not affected. The wallet now keeps the account's
existing representative, signs an explicitly chosen one, and refuses a malformed node answer before anything is
signed. https://github.com/dhyabi2/nano-mcp-public/pull/31
